我现在更建议把 Codex 的用法分成三层：

基础玩法：读文件、搜资料、看截图、先规划 进阶技巧：写规则、沉淀 Skill、管理上下文、生成交付物 
    
    
    高阶玩法：长期目标、并行开发、MCP 扩展、CI/审查自动化

这样分，比一上来讲“十大高阶玩法”更清楚。

因为对大多数人来说，真正的问题不是不会用高级功能。

而是基础用法还没跑顺，就开始折腾高级配置。

最后很容易变成：

功能看了一堆。

命令记了一堆。

真正工作里还是只会问一句：

帮我写一下xxx

我现在越来越觉得，Codex 最重要的不是某一个神奇命令。

而是你能不能把它放进真实工作流里。

有输入。

有过程。

有阶段结果。

有人工验收。

有最后交付。

有下次复用。

这篇就按这个顺序来讲：先讲基础用法，再讲进阶技巧，最后再讲高阶玩法。

高阶部分是我自己跑完的实战，我会尽量讲清楚它适合什么场景，以及小白什么时候再碰。

01

##  基础用法：先让 Codex 读文件，再让它回答

很多人用 Codex 的第一步，是直接问问题。

比如：

帮我分析一下这个选题。

这不是不能问。如果这样问显得codex和其他agent/龙虾没有什么不同了。

但如果你手里明明有资料，最好不要让它凭空分析。

更稳的问法是：

先读完这个 Markdown 文件，再帮我梳理它的结构、重点和可改写方向。

或者：

先看这个文件夹里的资料，不要凭印象回答。

这一步很基础。

但它决定了后面是不是空谈。

因为 AI 很容易根据常识写出一段“看起来对”的话。

但你不知道它到底有没有看过你的资料。我们给的资料越详细越好，ai最喜欢这种长文本了，为啥有的人用ai觉得幻觉太高了，根本原因在于输入的信息和限制条件不够。

不要先问观点，先让 Codex 看到证据。

适合场景：

读产品资料、竞品报告、长篇书籍、小红书账号拆解、截图 OCR ，或者别人整理好的素材卡。

![](https://mmbiz.qpic.cn/mmbiz_png/H159gTor6F4eDXBthARdg1sV4uHlTWo23BKyMuFc4372r3aQuYYxiaEOIbGSVQYRBibvFBh73VrKx6mN3XtIx08ITPAo5TOFaiaVLAib4RGt4MU/640?wx_fmt=png&from=appmsg)

这一层用顺了，Codex 才开始和普通聊天 AI 拉开差距。

因为它不只是“知道一些东西”。

它是真的在看你的文件。

02

##  基础用法：让它帮你搜文件、查字数、找关键词

Codex 能跑命令。

这点对非程序员也很有用。

比如你想知道：

哪个文件里提到了“反馈机制”？

这篇文章多少字？

哪个 HTML 是最新改的？

素材池里有哪些文件和xxx有关？

你不一定要自己会命令。

你可以直接说：

帮我在这个文件夹里搜索“xxx”，列出相关文件和位置。

或者：

帮我检查这篇文章有没有出现“xxxL”“ai”这类文字。

这类事情听起来不高级，很基础。

但是真正做内容、做电商、做 项目推进，资料一多，最痛苦的就是找不到。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/H159gTor6F4U1sbENpRK6AiaDiaVYOqZKsWRA7yHoFibTfZcFJaaLiaF0iatOtQgKw7NhNd1kuJib11ticI3YKwhdW9Vp6w7rmHnv1OwOAricMcWvoc/640?wx_fmt=png&from=appmsg)

Codex 在这里更像一个会用命令的资料管理员。

它可以帮你  |  找文件、找关键词、统计字数、检查图位、对比版本、看最近改动   
---|---  
  
把 Codex 当成本地工作台，你会少很多翻文件的时间。

03

##  基础用法：把截图交给它，但要让它说清楚看到了什么

Codex 可以处理图片输入。

这个能力很适合这几类场景：

看 UI 截图、报错截图、网页长图、网站截图、PPT封面、。

![](https://mmbiz.qpic.cn/mmbiz_png/H159gTor6F4teStiazgs9OPibUcTKFDfickVXYpViaHdfHFVWich4s8wszncB0xHeicjntl31iaDU0ibBg4fy8q1uxKBfApUsR5rxz7wtYAg9PC6msg/640?wx_fmt=png&from=appmsg)

但这里有一个坑。

不要一上来就问：

这张图为什么好？

这样太容易变成主观发挥。

我更建议分三步：

第一步：先只描述你看到了什么。 第二步：再区分哪些是事实，哪些是推测。 第三步：最后再给可复用结论。

比如拆解某个好看的小红书封面。

先看标题写了什么、字体大不大、主体图是什么、信息密度如何、有没有明确结果。

再判断它为什么吸引人。

这样拆出来的东西，才不会变成“这个封面很有冲击力”这种废话。

04

##  基础用法：大任务先用计划模式，不要一口气开干

原来的文章里讲“计划先行模式”，这个点我觉得应该提前讲。

因为它不是高阶玩法。

它应该是常用习惯。

只要任务稍微复杂一点，就不要直接让 Codex 开始做。

先让它计划。

这件事不要直接写。 请先列出你准备怎么做： 1. 要读哪些文件 2. 可能改哪些文件 3. 输出哪些中间结果 4. 哪些地方需要我确认

如果你在 CLI 里，也可以用 `/plan` 进入计划模式。

官方文档里也把 `/plan` 定位为让 Codex 先提出执行计划，再进入实现。

这个习惯非常重要。

因为它能把风险提前暴露出来。

你不需要等它写完 5000 字，才发现方向错了。

先看计划。

再让它做第一步。

再验收。

再继续。

不是文章里嘴上说反馈，而是任务推进时真的有反馈。

05

##  进阶技巧：用 AGENTS.md 给项目写说明书

到进阶阶段，第一件事是写规则。

在 Codex 里，`AGENTS.md` 很适合承担这个角色。

你可以把它理解成：

给 Codex 看的项目说明书。

里面可以写项目是做什么的、文件夹怎么分、常用命令是什么、哪些文件可以改、哪些文件不能乱碰、写作风格是什么、测试或验收标准是什么。

比如内容项目里，就可以写：

写正文前必须先立项。 HTML 必须按富文本规则。 图片不是装饰，是证据。

这类规则如果每次都靠嘴说，很容易漏。

写进规则文件之后，Codex 下次进入这个项目，就有了更稳定的工作边界。

官方 Slash command 文档里也提到，`/init` 可以生成 `AGENTS.md` 的脚手架，后面再人工修改成适合自己的版本。

06

##  进阶技巧：把重复流程沉淀成 Skill

如果同一件事你提醒了 Codex 三次，那就别再口头提醒了。

写成 Skill。

Skill 更像是给 Codex 的 SOP。

比如：资料怎么拆、账号怎么拆、热点怎么筛、素材怎么交接、HTML 排版要遵守什么限制。

![](https://mmbiz.qpic.cn/mmbiz_png/H159gTor6F7oCONHnuOS5OQo200YxwkIPrUKna75KhfLn8vvOHichqePsAqC6NrPSLWVQGN5z4lDWjMM8gWmkibeguBw5hqCpM9vicXJ9zTicqU/640?wx_fmt=png&from=appmsg)

这些都可以变成 Skill。

它的价值不是“显得高级”。

而是让 Codex 下次不用从零学。

以前  |  我每次重新告诉它规则。   
---|---  
后来  |  它先读取对应 Skill，再按规则做。   
  
这就是从“聊天”变成“工作系统”的关键。

高阶文章里经常会把 Skill 讲成一种很技术的东西。

但对小白来说，你可以先简单理解成：

把反复讲给 AI 听的话，写成一份固定说明。

07

##  进阶技巧：管理上下文，不要让一个对话扛所有任务

之前讲 `/clear`、`/compact`、`/resume`很实用。

只是我们要换个说法。

不要把它讲成“重置键”这么简单。

本质上，它是在管理上下文。

对话太长以后，容易出现：前面的要求被压缩、新任务被旧任务影响、Codex 开始引用不该引用的内容、你自己也分不清当前对话在做什么。

/compact  |  压缩长对话，保留关键上下文。   
---|---  
/new  |  在同一个 CLI 里开启新对话。   
/resume  |  恢复之前保存的会话。   
/fork  |  从当前对话分出一条新路径。   
/side  |  临时开一个侧边问题，不打断主线。   
  
这些命令不用一开始全记住。

但你要知道一件事：

不是所有任务都应该塞进同一个对话。

不然 Codex 乱，你也乱。

08

##  进阶技巧：生成交付物，而不是只生成回答

这是我自己感受最深的一点。

不要只让 Codex 回答你。

要让它生成可交付物。

可交付物  |  Markdown 草稿、HTML 文件、素材交接卡、拆解报告、流程图文案、小红书卡片脚本、检查清单、SOP   
---|---  
  
同样是问 AI，差别很大。

只生成回答，过几天就丢在对话里。

生成文件，后面还能继续改、继续引用、继续沉淀。

热点 -> 立项 -> 标题 -> 正文 -> 精简 -> 配图 -> HTML -> 预览 -> 复盘

每一步都有文件或结果。

这才叫工作流。

不是“AI 帮我写了一段话”。

而是“AI 参与了一次交付”。

09

##  高阶玩法：用 /goal 管长期目标，但别一上来就用

HTML 文件里把 `/goal` 放在非常核心的位置。

这个方向是对的。

官方文档里也提到，`/goal` 是一个实验功能，用来给长任务设置持续目标，需要开启对应实验特性。

![](https://mmbiz.qpic.cn/mmbiz_png/H159gTor6F5vpEpCibx7UYibC5D7icHXaxm4zia2QIDP0dELXcQRqs0Lejyd47CftnY8JNb0t0hmLuQPYWNsmV79tV3JXg8GKPuPo6DAwvH77HA/640?wx_fmt=png&from=appmsg)

它适合什么场景？

适合那种不是一次对话能做完的任务。

完成这次迁移，并保持测试通过。 把这个功能从规格文档推进到实现。 持续修复 review 里发现的问题，直到没有阻塞项。

但是小白不要一上来就用它。

因为长期目标有一个前提：

你得先知道目标怎么验收。

如果目标本身很模糊，`/goal` 只会让 Codex 更持久地跑偏。

先学会 `/plan`，再学会阶段验收，最后再考虑 `/goal`。

10

##  高阶玩法：Spec 驱动，不要只靠一句 Prompt

HTML 里还提到 Spec-Driven。

这个点很适合高阶工作流。

普通 Prompt 是这样：

帮我做一个会员系统。

Spec 驱动更像这样：

先写清楚： 1. 这个功能解决什么问题 2. 有哪些角色 3. 有哪些页面 4. 有哪些接口 5. 数据结构是什么 6. 什么情况算完成 7. 哪些边界不做

然后再让 Codex 按规格执行。

对复杂功能来说，规格文档比 Prompt 更重要。

因为 Prompt 容易一句话带过。

Spec 会逼你把需求摊开。

这对内容创作也有启发。

我们写报告也是一样。

不要直接说“写一篇市场调研报告”。

先写清目标是什么、痛点是什么、第一屏展示什么、结构怎么推进、哪些功能不能写满、哪些图必须补。

这本质上也是 Spec。

只是我们不叫它规格文档。

我们叫它立项。

11

##  高阶玩法：Worktree 并行开发，适合工程团队

Git Worktree 是原 HTML 里的一个重点。

它适合代码团队，不一定适合每个普通用户。

它解决的问题是：

多个任务同时进行时，不要都挤在同一个工作区。

一个分支修登录问题，一个分支重构用户中心，一个分支验证新功能。每个任务在独立 worktree 里跑，互不干扰。

这对工程团队很有价值。

但也要说清楚边界：

如果你还没有 Git 工作流基础，不建议一上来就并行开很多任务。

否则任务没提效，冲突先来了。

先把任务拆清楚 再确保每个任务互不影响 最后再考虑并行

不要反过来。

不是为了并行而并行。

12

##  高阶玩法：MCP、代码审查和自动化，最后再碰

最后讲一组真正高阶的东西：

MCP。

代码审查。

Headless / CI。

自动化任务。

这些都很强。

但我建议放在最后。

MCP  |  让 Codex 连接外部工具和上下文，比如 GitHub、浏览器、数据库、文档系统。   
---|---  
代码审查  |  在合并前帮你看逻辑风险、边界情况、测试缺口。   
Headless / CI  |  让 Codex 在非交互环境里跑，比如流水线、定时任务、PR 检查。   
  
这些玩法很适合工程化团队。

但对普通人来说，先不要急。

因为外部工具一多，风险也会上来：权限、密钥、数据安全、误操作、成本、日志追踪。

先跑通本地文件 再沉淀规则 再做阶段验收 再接外部工具 最后考虑自动化

不要一上来就追求“全自动”。

真实工作里，能稳定跑，比看起来高级更重要。

最后

##  我建议按这个顺序学

第一层：基础用法 1. 让它读文件 2. 让它搜文件 3. 让它看截图 4. 让它先规划  第二层：进阶技巧 5. 写 AGENTS.md 6. 沉淀 Skill 7. 管理上下文 8. 生成交付物  第三层：高阶玩法 9. /goal 长期目标 10. Spec 驱动 11. Worktree 并行 12. MCP / 审查 / 自动化

这套顺序不是为了显得系统。

而是为了少走弯路。

Codex 这类工具，最容易让人误判的地方是：你看见一个高级功能，就以为自己应该马上用。

但真实情况是：基础工作流没跑顺，高级功能只会放大混乱。

先让它读你的文件。

先让它产出一个能检查的小结果。

先把反复提醒的规则写下来。

先把一次实战沉淀成文件。

这些事情不酷，但它们最有用。

你现在用 Codex，更多是在“问问题”，还是已经开始让它处理文件、流程和交付物？

如果还停留在问问题，下一次可以先从一个真实文件开始。

让它读。让它整理。让它给你一个阶段结果。

这一步，可能比记住十个高阶命令更重要。
