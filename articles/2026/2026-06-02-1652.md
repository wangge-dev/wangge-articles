FEISHU + CODEX · LIGHT DATA FLOW

本篇讲小团队版的数据中台：不用复杂数仓，先用飞书表格、字段映射表和 Codex，把数据看起来。

很多人一听“数据中台”，脑子里会先冒出数据库、BI、权限、数仓、指标体系。

但对很多小团队来说，这一步没有这么重要。

更常见的问题是：数据明明都能拿到，却散在平台后台、Excel、本地文件夹和不同同事手里。

订单一份表，补单一份表，库存又是另外一个表。

每次想看数据，都要重新汇总一遍。

这篇文章讲的，就是怎么用一个轻量方案先把这件事跑起来。

我的思路很简单：  先把不同店铺的数据字段统一，再整理成一张标准订单表，然后放进飞书表格做明细、汇总和驾驶舱，最后让 Codex
辅助检查字段、生成简报和异常清单。

你可以把它理解成一个小团队版的数据中台雏形。看一下效果（这是codex自己生成的，我没有怎么调整，如果你有别的想法让codex改就行）：

01

##  先解决一个最基础的问题

我以前看数据，最麻烦的不是没有数据。

麻烦的是数据说法不统一。

比如同样是订单金额，店铺A可能叫“支付金额”，店铺B叫“实收金额”，店铺C叫“成交金额”。

同样是 SKU，有的平台叫“商品编码”，有的平台叫“商家编码”。

字段名不同，金额口径不同，订单号格式也可能不同。

如果这一步不处理，后面不管用飞书、Power Query、RPA，还是让 Codex 分析，都会被同一个问题拖住：这些表到底能不能合到一起？

所以第一步不是做可视化。第一步是先把数据叫法统一。特别是多平台的这种：

![](https://mmbiz.qpic.cn/mmbiz_png/H159gTor6F5ugbbV6Y4c7Z3zXeLLSFc985OicKZLXyRALviaTqvh0icewcZoWwpbzBNTkMZSmqDFQrYqo8p4fMTeaQAUOhf3h0t4aeqjWR7r3Q/640?wx_fmt=png&from=appmsg)

02

##  从 0 开始，需要准备什么

先不要想太复杂。

如果你只是想复刻一个最小版本，准备几个店铺导出的订单表、一张字段映射表、一张标准订单表、一个飞书多维表格或在线表格，再准备一个能读文件、写脚本、调用飞书
CLI 的 Codex 环境，就够了。

如果没有 RPA，没有 Power Query，也可以先做。

手动导出订单表，手动整理字段映射，先把标准订单表跑起来。

等流程稳定后，再让 RPA 定时导出，让 Power Query 或脚本自动清洗，让飞书承接数据，让 Codex 生成日报。

这就是这套方案的顺序：先手动跑通，再逐步自动化。

03

##  公开展示为什么用模拟数据

真实数据不方便展示，所以我把公司名、店铺名和真实订单数据都换成了模拟口径。

文章里只用店铺A、店铺B、店铺C。

订单表通常能看到来源店铺、订单日期、订单号、商品、SKU、数量、金额

但 补单、库存，不是订单表自带的。

它们还需要广告花费、退款订单、补单，库存表这些额外数据。

所以文章里出现的 ROI模拟、退款率模拟、库存风险模拟，主要是为了展示驾驶舱可以怎么扩展。

如果你自己有推广、退款、补单、库存这些数据，可以继续交给 Codex、其他 Agent，或者用 Excel 处理后，再统一放进标准表。

![](https://mmbiz.qpic.cn/mmbiz_png/H159gTor6F4n19iblyj7lhkwckvH3jWEzHWZnJUR4wbDeZEkz4pUdxFXplW4d87eNvlUR1gr68zUYhXAOp7sLGsHrsT6BWXqErOsiaDkP7MnA/640?wx_fmt=png&from=appmsg)

04

##  第一步：做字段映射表

字段映射表是这套流程的核心。

它的作用不是计算指标，而是翻译字段。

标准字段  |  店铺A  |  店铺B  |  店铺C   
---|---|---|---  
来源店铺  |  固定写店铺A  |  固定写店铺B  |  固定写店铺C   
订单日期  |  支付时间  |  下单时间  |  成交时间   
订单号  |  订单编号  |  主订单号  |  订单号   
商品名称  |  商品标题  |  商品名称  |  宝贝标题   
SKU  |  商品编码  |  SKU  |  商家编码   
GMV模拟  |  支付金额  |  实收金额  |  成交金额   
  
有了这张表，几个店铺的数据才能进入同一张标准订单表。

这里有两个小坑。订单号、商品 ID、SKU，  不要当数字处理，要按文本处理  。金额、数量、退款金额，才按数字处理。

很多订单号很长，一旦被表格当成数字，后面几位可能直接变成 0。

05

##  第二步：建一张标准订单表

标准订单表不用一开始做得很大。

小数据量先保留 10-15 个字段就够了。

来源店铺、订单日期、订单号、商品名称、SKU、数量、GMV模拟、实收金额模拟、退款金额模拟、渠道模拟、活动模拟、异常标记。

这里最重要的一句话是：没有的数据不要编。

驾驶舱可以先简单，数据口径不能先乱。

06

##  第三步：把标准订单表放进飞书

飞书的优势不是“它也是表格”。

它更适合做一个轻量的数据协作层。

本地 Excel 只能自己看。飞书表格可以让团队在线查看、协作、评论、做权限控制，也方便后面接机器人、消息提醒和自动化。

我建议飞书里先放三层：  明细表存标准订单，汇总表按店铺、日期、商品、类目、活动做统计，驾驶舱只展示核心指标、趋势、排行和异常提醒。

07

##  Codex 在这里具体做什么

Codex 不是替你做经营决策。

它更像一个执行助理。

这套流程里，我会让它读取本地 Excel / CSV，对比不同店铺导出的字段，生成字段映射表，整理标准订单表，检查订单号和 SKU
是否被当成数字，提醒哪些字段缺失，再通过飞书 CLI 读取表格、更新字段、写入记录，最后输出经营简报和异常清单。

飞书 CLI 的价值在这里。

如果只在浏览器里手动操作，很多事情还是靠人点。有了飞书 CLI，Codex 就可以在你授权之后，查询表格、字段、记录，也可以帮你检查结构和生成文档。

08

##  哪些可以自动化，哪些要人工确认

这套流程后面可以自动化

可以自动化的部分包括：RPA 定时导出文件、Power Query
或脚本刷新清洗、标准订单表生成、飞书记录批量写入、经营日报和异常初筛、字段类型和缺失字段检查。

但第一次飞书应用授权、权限配置、指标口径、驾驶舱最终排版、异常数据背后的业务决策、真实数据脱敏和公开截图处理，最好人工确认。

这里不是说 Codex 不能参与。Codex 可以列字段、写脚本、生成校验表、检查敏感信息，也可以给驾驶舱排版建议。

但最后确认的人还是  你  。尤其是指标口径，不同团队对 GMV、实收金额、退款率、ROI 的算法可能不一样，不能让 AI 自己编。

09

##  不会 Power Query 怎么办

可以先不用。

Power Query 适合处理每周都要重复清洗很多文件的场景。

但如果你只是先搭一个最小版，可以走更简单的路线：每个店铺导出最近 7 天或 30
天订单，用字段映射表把字段对齐，整理成标准订单表，检查订单号、SKU、金额、数量、日期类型，导入飞书，再做明细表、汇总表和驾驶舱。

等这条链路跑顺了，再上 Power Query、RPA、n8n 或数据库。

10

##  我整理了一份可以直接给 Agent 用的起步包

为了不让这篇只停留在思路层，我把这套流程整理成了一份起步包。

它不是一个复杂系统，更像一套可以直接交给 Agent 的执行材料。

里面包括通用执行提示词、字段映射表模板、标准订单表模板、输入资料卡模板、异常检查清单、飞书三层搭建 SOP、三份脱敏模拟订单数据。

你可以把这套包直接给  Claude、OpenClaw、Hermes、Codex  。

有真实数据，就把模拟数据替换掉。没有真实数据，也可以先让 Agent 用模拟数据跑一遍。

##  可以直接给 Codex 或其他 Agent 的提示词

如果你想先跑一个最小版本，可以这样问：

text

请帮我把下面三份店铺订单表统一成一张标准订单表。  请先输出字段映射表，再列出缺失字段和字段类型问题。  我的标准字段是： 来源店铺、订单日期、订单号、商品名称、SKU、数量、GMV模拟、实收金额模拟、退款金额模拟、渠道模拟、活动模拟、会员模拟、异常标记。  要求： 1. 订单号和 SKU 必须按文本处理。 2. 金额和数量按数字处理。 3. 没有的数据不要编造，标成“暂无数据”或留空。 4. 如果没有广告花费，不要计算 ROI。 5. 如果没有退款字段，不要计算退款率。 6. 最后给我一份可导入飞书的标准订单表结构。

这段提示词的重点不是让 AI 直接给你经营结论。

而是先让它把字段、类型、缺失数据检查清楚。

这一步稳了，后面接飞书、Excel、脚本都会顺很多。

12

##  其他 Agent 能不能做

能，但要看它能不能接工具。

Claude Code 适合写脚本、改配置、解释复杂逻辑。OpenClaw 或龙虾更适合补浏览器操作，比如在页面里点选、导出、检查。

Hermes 更适合长期日报、消息推送、多 Agent 分工。n8n 适合在流程稳定后做定时编排。Dify、Coze 更适合把结果封装成团队可用的问答助手。

我这次先选 Codex，是因为第一版搭建阶段要频繁看本地文件、改脚本、读飞书表、生成报告文件和流程记录。

流程稳定以后，完全可以把定时运行交给 n8n，把消息提醒交给 Hermes，把问答入口交给 Dify。

13

##  最后说一下

这篇不是让大家照着搭一个一模一样的飞书表格。

我更想分享的是一个顺序：  先统一字段，再统一标准订单表，再用飞书做轻量驾驶舱，最后让 Codex 帮你检查、执行、记录和生成简报。

先把这条链路跑起来，再决定后面要不要接 RPA、Power Query、n8n、Dify、Hermes 或更完整的数据平台。

先让数据能看，口径能对，问题才能被发现。

这一步做好，后面的自动化才有意义。
